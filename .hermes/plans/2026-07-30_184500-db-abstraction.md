# Database Abstraction Layer — SQLite default, PostgreSQL/MariaDB optional

> **For Hermes:** Use OpenCode to implement this plan task-by-task.

**Goal:** Replace direct `sqlite3` calls with a pluggable database abstraction so the relay can run on SQLite (default), PostgreSQL, or MariaDB without changing business logic.

**Architecture:** A `Database` protocol/ABC with three implementations (`SqliteDatabase`, `PostgresDatabase`, `MariadbDatabase`). The active backend is selected via `db_type` in `config.yaml`. All existing `get_conn()` callers are migrated to use the new interface. Schema management (`_schema`, migrations) stays per-backend.

**Tech Stack:** `sqlite3` (stdlib), `asyncpg` (PostgreSQL), `aiomysql` or `pymysql` (MariaDB), `pydantic-settings` (config)

**Non-goals:**
- No ORM (SQLAlchemy etc.) — keeps it lightweight
- No query builder — raw SQL per backend, shared where possible
- No migration framework — `_run_migrations` stays per-backend

## Proposed approach

### Layer 1: Database protocol + config

A `Database` protocol defines the shared interface. Each backend implements it. The config gets a `db_type` field.

### Layer 2: Backend implementations

- **SqliteDatabase** — wraps current `get_conn()` logic, WAL mode, Row factory, retry-on-locked
- **PostgresDatabase** — uses `asyncpg` connection pool, `$1` placeholders, `asyncpg.Row`
- **MariadbDatabase** — uses `aiomysql` or `pymysql`, `%s` placeholders

### Layer 3: Migration path

1. Define `Database` protocol
2. Extract `SqliteDatabase` from current `db.py`
3. Update config (`db_type: sqlite | postgres | mariadb`)
4. Migrate all callers from `get_conn()` to `db.get_conn()`
5. Add `PostgresDatabase` + `MariadbDatabase` stubs (full implementation deferred)
6. Tests: existing tests keep passing with SQLite

```python
def create_database() -> Database:
    if settings.db_type == "sqlite":
        return SqliteDatabase(settings.db_path)
    elif settings.db_type == "postgres":
        return PostgresDatabase(settings.pg_dsn)
    elif settings.db_type == "mariadb":
        return MariadbDatabase(settings.mariadb_dsn)
    else:
        raise ValueError(f"Unknown db_type: {settings.db_type}")
```

## Risks and tradeoffs

| Risk | Mitigation |
|------|-----------|
| **Placeholder syntax differs** (`?` vs `$1` vs `%s`) | Each backend handles its own placeholder style. Shared queries use a common subset or get overridden. |
| **SQLite-specific SQL** (e.g. `strftime`, `PRAGMA`) | Backend-specific `_schema()` methods. Shared queries avoid SQLite-isms. |
| **Async vs sync** (sqlite3 is sync, asyncpg is async) | Keep `get_conn()` sync for now. PostgreSQL backend wraps async calls in `asyncio.to_thread` or uses a sync wrapper. |
| **Connection pool** (sqlite3 is per-call, asyncpg uses pool) | `PostgresDatabase` manages a pool internally. `close()` releases it. |
| **Migration complexity** | `_run_migrations()` is per-backend. No shared migration state. |

---

## Open questions

1. **Async vs sync for PostgreSQL?** — Current codebase is sync-with-threads. asyncpg is async-native. Proposal: keep sync interface, use `asyncpg.connect()` in a thread wrapper.
2. **MariaDB driver?** — `aiomysql` (async) or `pymysql` (sync). Proposal: `pymysql` for simplicity, matches current sync pattern.
3. **Test coverage for non-SQLite backends?** — Deferred until a backend is actually implemented. CI runs SQLite only.
